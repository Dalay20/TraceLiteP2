AUDITORÍA TÉCNICA DE TRACELITE
Avance parcial - Sistemas Operativos

Fecha de revisión: 2026-11-06

Alcance
--------

Se revisó la implementación actual de TraceLite en C para GNU/Linux, sin
modificar el código fuente ni los documentos existentes. La compilación de
verificación se realizó en /tmp para no alterar los ejecutables del proyecto:

gcc -Wall -Wextra -g -o /tmp/tracelite-main main.c services.c
gcc -Wall -Wextra -g -o /tmp/tracelite-collector collector.c
timeout 10 /tmp/tracelite-main

La ejecución de prueba terminó correctamente y el collector recibió 11 spans:
cuatro de api, cuatro de inventario y tres de pagos. La cuarta solicitud no
generó span de pagos porque el stock inicial es tres unidades.


1. CORRECTO: FUNCIONALIDADES IMPLEMENTADAS CORRECTAMENTE

1.1 Arquitectura de procesos

Resultado: CORRECTO.

- main es el proceso principal y crea las pipes en main(), en main.c:9-14.
- collector se crea mediante fork() en main.c:17 y el hijo ejecuta
  execl("./collector", "collector", NULL) en main.c:24-27.
- pagos se crea como proceso independiente mediante fork() en main.c:30-40.
- inventario se crea como proceso independiente mediante fork() en
  main.c:42-53.
- api se crea como proceso independiente mediante fork() en main.c:55-65.
- Todos los procesos de servicio son hijos directos de main. La relación
  estática es:

      main
      |-- collector (fork + exec)
      |-- pagos (fork)
      |-- inventario (fork)
      `-- api (fork)

- main espera a los cuatro hijos con waitpid() en main.c:74-77.
- Cada servicio se implementa en una función que se ejecuta dentro de su
  propio proceso, pero la comunicación entre servicios ocurre por pipes y no
  por llamadas directas entre funciones.

Sobre los PID:

- La relación padre-hijo puede determinarse por la secuencia de fork() y
  waitpid().
- El programa no imprime getpid() ni getppid(), por lo que no registra los
  valores numéricos de los PID durante la ejecución. El requisito de
  independencia se cumple, pero no existe evidencia visible de PID en la
  salida de terminal.

1.2 Cierre de descriptores

Resultado: MAYORMENTE CORRECTO.

- collector cierra pipe_spans[1] y todas las pipes de servicios antes de
  duplicar pipe_spans[0] a stdin, en main.c:19-25.
- pagos conserva pipe_ib[0], pipe_bi[1] y pipe_spans[1], y cierra los demás
  extremos en main.c:33-38.
- inventario conserva pipe_ai[0], pipe_ib[1], pipe_bi[0], pipe_ia[1] y
  pipe_spans[1], cerrando los demás en main.c:45-51.
- api conserva pipe_ai[1], pipe_ia[0] y pipe_spans[1], y cierra los demás en
  main.c:58-63.
- main cierra todos sus descriptores después de crear los hijos, en
  main.c:67-72.
- api cierra pipe_ai y su salida de spans al terminar, en services.c:47-49.
- inventario cierra pipe_ib, pipe_ia y su salida de spans al terminar, en
  services.c:98-102.
- pagos cierra su entrada y pipe_bi, además de su salida de spans, en
  services.c:139-141.

Este cierre permite que EOF se propague de api a inventario y de inventario a
pagos. La ejecución de prueba confirma que los procesos terminan sin quedar
bloqueados.

1.3 Comunicación IPC

Resultado: CORRECTO EN EL FLUJO NORMAL.

Las cinco pipes se crean en main.c:10-14:

- pipe_ai: api -> inventario.
- pipe_ib: inventario -> pagos.
- pipe_bi: pagos -> inventario.
- pipe_ia: inventario -> api.
- pipe_spans: api, inventario y pagos -> collector.

Los servicios intercambian mensajes mediante write(), fgets() y descriptores
heredados después de fork():

- api escribe el contexto en pipe_ai en services.c:29-32 y lee la respuesta
  desde pipe_ia en services.c:34-36.
- inventario lee pipe_ai en services.c:55-60, escribe a pagos en
  services.c:87-89 y lee la respuesta de pagos en services.c:91-95.
- pagos lee pipe_ib en services.c:108-111 y responde por pipe_bi en
  services.c:135-136.

No existe una llamada de función de api a inventario o de inventario a pagos
para realizar la comunicación. Cada función se ejecuta en un proceso diferente
y recibe descriptores de pipes.

El collector recibe la salida combinada de los tres servicios mediante su
entrada estándar. La conexión se realiza con dup2() en main.c:24 y el collector
lee hasta EOF en collector.c:54-61.

1.4 Propagación del contexto

Resultado: CORRECTO EN LA IMPLEMENTACIÓN ACTUAL.

- api crea un Trace ID y su Span ID para cada solicitud en services.c:17-24.
- api envía ambos identificadores y el número de solicitud a inventario en
  services.c:29-32.
- inventario conserva el Trace ID y establece como parent_span_id el Span ID
  de api en services.c:65-70.
- inventario envía a pagos el Trace ID y el Span ID de inventario en
  services.c:87-89.
- pagos conserva el Trace ID, usa el Span ID de inventario como
  parent_span_id y genera su propio Span ID en services.c:116-122.

La jerarquía esperada queda implementada como:

    api -> inventario -> pagos

Los IDs se generan con gen_id() en span.h:40-43. En una ejecución normal cada
solicitud recibe un Trace ID diferente y los spans observados compartieron el
Trace ID correspondiente.

1.5 Manejo de errores y estados

Resultado: CORRECTO SEGÚN LA LÓGICA IMPLEMENTADA.

- pagos establece ERROR para la solicitud número 3 o con una probabilidad
  aleatoria del 10 %, en services.c:127-133.
- pagos envía OK o ERROR a inventario en services.c:135-136.
- inventario puede tener estado OK aunque pagos termine en ERROR, porque su
  propio span se cierra antes de ejecutar pagos, en services.c:73-80.
- Si pagos falla, inventario propaga ERROR a api mediante pipe_ia, en
  services.c:91-95.
- api refleja la respuesta final en su estado, en services.c:34-44.
- Si no hay stock, inventario genera ERROR, envía ERROR a api y continúa sin
  escribir en pipe_ib, en services.c:75-85. Por tanto pagos no se ejecuta para
  esa solicitud.

La ejecución de prueba mostró ambos casos: una traza con inventario OK y pagos
ERROR, y una traza con inventario ERROR sin span de pagos.

1.6 Medición, serialización y reconstrucción

Resultado: CORRECTO EN EL CASO NORMAL.

- ahora_ms() utiliza clock_gettime(CLOCK_MONOTONIC) en span.h:25-30.
- La duración se calcula como fin_ms - inicio_ms en api, inventario y pagos:
  services.c:39-40, services.c:77-78 y services.c:131-132.
- span_serializar() produce nueve campos separados por | y termina cada span
  con salto de línea, en span.h:32-38.
- collector conserva el campo parent_span_id vacío del span raíz porque usa
  strsep(), en collector.c:15-34.
- collector agrupa por Trace ID en collector.c:63-72.
- imprimir_arbol() busca hijos comparando Trace ID y parent_span_id, en
  collector.c:37-51.


2. PROBLEMAS: ERRORES TÉCNICOS ENCONTRADOS

Problema 1 - No se comprueba el resultado de fork()
----------------------------------------------------

Archivo: main.c
Función: main()
Líneas: 17, 31, 43 y 56

Las llamadas a fork() solo distinguen el caso pid == 0. No se comprueba el
caso pid == -1. Si fork() falla, main continúa como si el proceso hijo
existiera, puede cerrar descriptores y ejecutar waitpid() con un PID inválido.
Esto puede producir un flujo incompleto o una espera que no representa el
estado real del sistema.

Problema 2 - No se comprueba dup2(), execl(), fdopen() ni close()
------------------------------------------------------------------

Archivos: main.c y services.c
Funciones: main(), servicio_a(), servicio_inventario() y servicio_b()
Líneas principales: main.c:24-27; services.c:15, 36, 55-56 y 108

execl() sí tiene perror() si falla, pero no existe una validación general de
dup2(), fdopen() ni close(). Si dup2() falla, collector no recibe los spans por
stdin. Si fdopen() falla, una llamada posterior a fgets() puede provocar un
fallo. Las funciones de servicio tampoco notifican estos errores a main.

Problema 3 - Se ignoran errores y escrituras parciales de write()
-----------------------------------------------------------------

Archivos: span.h y services.c
Funciones: emitir_span(), servicio_a(), servicio_inventario() y servicio_b()
Líneas: span.h:47-50; services.c:32, 83, 89, 94-95 y 136

Todas las llamadas a write() ignoran su valor de retorno. PIPE_BUF garantiza
atomicidad para una escritura de tamaño permitido, pero no garantiza que una
llamada interrumpida escriba todos los bytes solicitados. Si write() retorna
un número menor, se pierde parte del mensaje y el receptor puede obtener una
línea incompleta o un contexto inválido.

El comentario de span.h:45-46 afirma que la línea es menor que PIPE_BUF, lo
que protege contra la mezcla entre escritores, pero no resuelve por sí solo el
tratamiento de escrituras parciales o errores EINTR.

Problema 4 - No se comprueban errores de lectura ni mensajes inválidos
----------------------------------------------------------------------

Archivos: services.c y collector.c
Funciones: servicio_a(), servicio_inventario(), servicio_b() y
span_parsear()
Líneas principales: services.c:36, 63, 92-93 y collector.c:20-34

Los servicios tratan EOF como ERROR, lo cual es una decisión segura para api,
pero no diferencian EOF de un error de lectura. Además, las respuestas se
aceptan como cualquier texto distinto de los primeros cinco caracteres de
ERROR, lo que convierte mensajes inesperados en OK.

collector.c valida que existan nueve campos, pero usa atof() sin comprobar si
los campos numéricos son válidos. Una línea con texto no numérico puede
convertirse silenciosamente a cero.

Problema 5 - Generación de IDs probabilística
---------------------------------------------

Archivo: span.h
Función: gen_id()
Líneas: 40-43

Los IDs se forman con rand(). No existe una comprobación de colisiones ni un
generador criptográficamente fuerte. Para una demostración académica es
aceptable, pero el requisito de unicidad se cumple solo probabilísticamente,
no como garantía formal.


3. MEJORAS: ASPECTOS QUE PODRÍAN OPTIMIZARSE

3.1 Manejo de escrituras completas

Archivo recomendado: span.h y, opcionalmente, un helper compartido.

Crear una función write_all() que repita write() hasta enviar todos los bytes,
gestione EINTR y devuelva un error explícito. Usarla para spans, contextos y
respuestas.

3.2 Validación centralizada de mensajes

Archivo recomendado: services.c y span.h.

Definir funciones para validar el formato del contexto, limitar el número de
solicitud y aceptar únicamente las respuestas exactas OK\n o ERROR\n. Esto
evita que un mensaje corrupto sea interpretado como una operación válida.

3.3 Diagnóstico de procesos

Archivo recomendado: main.c.

Registrar getpid(), getppid() y el nombre del proceso al iniciar. Esto permitiría
demostrar visualmente los PID solicitados en la auditoría y facilitaría el
diagnóstico de bloqueos o terminaciones anómalas.

3.4 Estado de inventario más realista

Archivo recomendado: services.c.

El inventario actual usa un único contador global de tres unidades y descuenta
la unidad antes de que pagos confirme el cobro. Para un sistema más realista
convendría definir reserva, confirmación y liberación de stock cuando el pago
falla. Esto es una mejora funcional, no un incumplimiento del objetivo mínimo
del avance.

3.5 Validación numérica en collector

Archivo recomendado: collector.c.

Reemplazar atof() por una conversión que permita detectar errores, por ejemplo
strtod() con comprobación del puntero final y del rango. También se podrían
validar estado, longitud de IDs y relaciones padre-hijo.

3.6 Control de capacidad

Archivo recomendado: collector.c.

Cuando n alcanza MAX_SPANS, el collector deja de leer y sale del bucle
collector.c:58-60. Si todavía hay escritores, podrían recibir SIGPIPE o
perderse spans. Se debe aumentar la capacidad, continuar leyendo y reportar el
exceso, o coordinar explícitamente el límite.


4. INCUMPLIMIENTOS: REQUISITOS QUE NO SE CUMPLEN COMPLETAMENTE

Incumplimiento 1 - Gestión completa de escrituras y lecturas IPC
----------------------------------------------------------------

Estado: PARCIAL.

El flujo utiliza correctamente pipes y funciona en la ejecución normal, pero
no gestiona write() parcial, EINTR ni errores de escritura. Por tanto, el
requisito de gestión robusta de mensajes IPC no está completamente cumplido.

Evidencia: span.h:47-50 y services.c:32, 83, 89, 94-95 y 136.

Incumplimiento 2 - Unicidad garantizada de Trace ID y Span ID
----------------------------------------------------------------

Estado: PARCIAL.

Cada solicitud genera nuevos valores, pero rand() no garantiza que no existan
colisiones. El comportamiento cumple la expectativa práctica del ejemplo, no
una garantía estricta de unicidad.

Evidencia: span.h:40-43.

Incumplimiento 3 - Identificación observable de PID
---------------------------------------------------

Estado: NO EVIDENCIADO EN LA SALIDA.

Los procesos sí son independientes y la relación padre-hijo es correcta, pero
el programa no muestra sus PID. Si el enunciado exige capturas o una tabla
basada en PID reales, falta instrumentación de diagnóstico.

Evidencia: main.c:17-77; no existe uso de getpid() o getppid() en main.c.

Incumplimiento 4 - Verificación explícita de fallos del sistema
----------------------------------------------------------------

Estado: PARCIAL.

Solo pipe() y la ejecución fallida de exec() tienen manejo explícito. fork(),
dup2(), fdopen(), close() y las operaciones write() no tienen comprobación
completa.

Evidencia: main.c:11-13 y 24-27; services.c:15, 32, 55-56, 83, 89, 94-95 y
136.

No se identificaron incumplimientos en la jerarquía api -> inventario -> pagos,
la recepción de spans por el collector, el uso de CLOCK_MONOTONIC, el cálculo
de duraciones ni la propagación normal de estados.


5. RECOMENDACIONES: CAMBIOS PROPUESTOS Y ARCHIVOS

Prioridad alta:

1. Implementar write_all() en span.h o en un nuevo helper compartido y usarlo
   desde emitir_span() y todas las respuestas de services.c.
2. Comprobar fork(), dup2(), fdopen(), close() y write() en main.c y
   services.c. Reportar errores con perror() y terminar el proceso afectado
   con un estado no exitoso.
3. Comprobar el resultado de execl() y hacer que main pueda detectar una
   finalización anormal mediante waitpid() y WIFEXITED/WIFSIGNALED.

Prioridad media:

4. Validar estrictamente contextos, respuestas y números en services.c y
   collector.c.
5. Sustituir atof() por strtod() con detección de campos inválidos en
   collector.c.
6. Agregar mensajes de diagnóstico con getpid() y getppid() en main.c, sin
   mezclarlos con las líneas de spans.

Prioridad funcional:

7. Decidir si una reserva de inventario debe liberarse cuando pagos falla. Si
   esa semántica es requerida, ajustar servicio_inventario() en services.c
   para separar reserva, confirmación y liberación.
8. Definir qué debe ocurrir si el collector supera MAX_SPANS y modificar
   collector.c para no abandonar silenciosamente la lectura.

Conclusión
----------

La implementación actual cumple la arquitectura principal del avance: main
crea procesos independientes para api, inventario y pagos; collector usa
fork/exec; la comunicación se realiza mediante pipes; el contexto se propaga
con la jerarquía api -> inventario -> pagos; y los estados y spans se muestran
correctamente en una ejecución normal.

No se recomienda modificar la arquitectura. Antes de considerar el avance
completamente robusto, deben corregirse principalmente las escrituras parciales,
la comprobación de errores de llamadas al sistema y la validación de mensajes.
La ausencia de PID visibles y la unicidad probabilística de IDs deben tratarse
según el nivel de evidencia exigido por el enunciado.

6. ESTADO POSTERIOR A LAS CORRECCIONES

Después de esta auditoría se implementaron las correcciones solicitadas:

- `write_all()` en span.h para gestionar escrituras completas, interrupciones
  EINTR y errores de pipe.
- Comprobación de fork(), dup2(), fdopen(), waitpid(), write() y varias
  operaciones de cierre en main.c y services.c.
- Validación de contextos, respuestas, IDs, estados y valores numéricos de
  spans en services.c y collector.c.
- Diagnóstico de PID y PPID para collector, pagos, inventario y api mediante
  stderr.
- El collector continúa leyendo hasta EOF y reporta líneas inválidas en lugar
  de descartarlas silenciosamente al alcanzar MAX_SPANS.

Validaciones ejecutadas:

1. `make` terminó correctamente.
2. `make clean && make CFLAGS='-Wall -Wextra -Werror -g'` terminó sin
   advertencias.
3. `./main` completó las cuatro solicitudes sin bloqueo.
4. Se recibieron 11 spans: cuatro de api, cuatro de inventario y tres de pagos.
5. Se reconstruyeron las trazas api -> inventario -> pagos.
6. La cuarta solicitud terminó en inventario por falta de stock y no ejecutó
   pagos.
7. Un span inválido enviado manualmente al collector fue rechazado y reportado
   por stderr.

La unicidad de IDs continúa siendo probabilística porque gen_id() usa rand().
Si el enunciado exige una garantía estricta de unicidad, todavía debe
sustituirse por un generador con control de colisiones.
